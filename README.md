# Windows 网络极速优化 / Windows Network Booster

> 你的网速，可能正被 Windows 的"默认保守设置"偷偷按住。
> 一键解除 Windows 对网络性能的限制 —— 作者实测网速**史诗级**提升。

一个 PowerShell 一键脚本（`net-boost.bat` 外壳 + `net-boost.ps1` 引擎），10 步完成系统级网络优化，全程中文菜单、可一步步执行、可一键恢复默认。

**⚠️ 本工具修改的是系统级网络栈设置，使用前请先读完 README。**

---

## 用途：它解决什么

Windows 出于"兼容性优先"的默认策略，会对网络做大量保守限制。本工具把这些限制一次性解除：

| # | 优化项 | 说明 |
|---|--------|------|
| 1 | 记录原电源方案 | 优化后可一键恢复原状 |
| 2 | 刷新 DNS 缓存 | 清理失效的 DNS 解析 |
| 3 | 重置 Winsock / IP 协议栈 | 修复协议栈损坏导致的异常降速 |
| 4 | TCP 全局优化 | 开启 RSS / TCP Fast Open / ECN，关闭时间戳；Compound TCP 拥塞控制 |
| 5 | 高性能电源计划 | 防止网卡"省电降频"导致的断流、降速 |
| 6 | 解除 QoS 预留带宽 | 解除系统预留带宽 |
| 7 | 解除多媒体网络节流 | **Windows 默认限速 10 包/秒，这里直接解除** |
| 8 | 关闭 Nagle 算法 | 降低小包延迟，游戏 / SSH / 实时交互更跟手 |
| 9 | 关闭 Windows 更新 P2P | 阻止系统在后台偷偷上传、占满上行 |
| 10 | 关闭 IPv6（可选） | 减少双栈 DNS 连接超时，开关在脚本顶部 |

## 日常使用痛点（实话实说）

- **下载跑不满带宽** —— 多媒体网络节流 + QoS 预留 + 更新 P2P 三方夹击，这是最常见的原因
- **游戏 / 视频会议延迟高** —— Nagle 算法让小包在缓冲区排队
- **笔记本电池模式下网速明显变慢** —— 网卡被电源计划"降频省电"
- **挂了代理依然不流畅** —— 本工具优化的是系统这一层，与 v2rayN / Clash 等代理互补；**但如果瓶颈在代理节点本身，请先排查代理，本工具救不了代理**
- **中文系统下传统 .bat 工具乱码、闪退、跑完无效** —— 我们踩穿了 cmd 解析 UTF-8 批处理的坑（见下文），用 PowerShell 引擎重写，中文显示完美、流程稳定

## 使用方法

1. 下载 `net-boost.bat` 和 `net-boost.ps1`，放在**同一个文件夹**
2. 双击 `net-boost.bat`
3. 提示权限时选 `Y`（自动提权）；或右键 → 以管理员身份运行
4. 主菜单：`1` 一步步执行（第一次使用推荐） / `2` 一键全自动 / `3` 恢复默认
5. 跑完 10 步查看校验结果 → 选 `Y` 重启电脑（**必须重启才完全生效**）

## 效果

作者在 Windows 11（x64，开启 UTF-8 全球语言支持）实测：运行后网速"史诗级"提升。
不同机器、不同网络环境效果不同，**不保证人人都能起飞** —— 但如果你的网速确实被上述默认限制按住过，值得一试。

## 一键恢复

重新运行脚本，主菜单选 `3`：

- 重置 Winsock / IP / TCP 协议栈到系统默认
- 删除全部注册表改动（QoS / 多媒体节流 / 传递优化 / Nagle / IPv6）
- 恢复优化前的电源方案

## 为什么是 bat + ps1 两个文件

血泪教训：**cmd.exe 解析含中文的 UTF-8 批处理文件不可靠** —— 多字节字符导致行读取错位，命令被拆成碎片、`call` 标签找不到、最终 `BATCH RECURSION exceeds STACK limits` 无限递归崩溃；`chcp` 和 GBK 编码都救不了。所以：

- `net-boost.bat`：纯 ASCII 外壳，只有一行调用，零解析风险
- `net-boost.ps1`：UTF-8 (BOM) PowerShell 引擎，承载全部逻辑与中文界面，原生支持自提权、交互菜单、分步确认

## 兼容性与风险

- Windows 10 / 11（x64），需要管理员权限
- 公司管控设备、特殊网络环境请先确认合规
- 所有改动均可通过"恢复默认"回退；脚本不驻留、不联网、不留后台进程
- 重启前请保存好其他工作

## 为什么开启 ECN（不再关闭）

早期（2000 年代）部分防火墙/中间设备会丢弃带 ECN 标记的包，所以很多"网络优化脚本"习惯性关闭 ECN。现在这已过时——主流网络和主流服务器（Cloudflare/Google/AliDNS/Bing 等）都支持 ECN 协商。

实地抓包验证（Win11，2026-08）：本机开启 ECN 后，10/10 个出站 TCP SYN 带 ECE+CWR 位发起协商，5/10 个服务端 SYN-ACK 回 ECE 同意，传输阶段 15 个数据包在 IP 层被标 ECT——机制是活的。关闭 ECN 时这些全部为 0，拥塞只能靠丢包反馈，导致重传和抖动。

ECN 的收益是"保险"：路径拥塞时路由器用 CE 标记代替丢包，减少重传和延迟尖峰。日常无拥塞时无差异，但拥塞发生时差距明显。
